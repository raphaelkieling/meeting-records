## Design and Delivery Approach

### Storage

Extract only the shared connection/schema handling needed by load/create/rename, keeping SQLite handles scoped to one actor operation and finalized on all paths. Initialize fresh databases directly at v2; migrate valid v1 databases transactionally. Validate v1 rows before committing migration so invalid historical records do not become a partially successful upgrade. Unknown versions, malformed schema, and invalid rows fail without destructive repair.

Use prepared statements with bound UUID/name/timestamp values. `createMeeting(id:name:)` returns a committed Meeting; the caller creates one UUID per deliberate creation. Repeating the same creation ID returns the existing record without overwriting it, so an internal retry cannot insert twice. `renameMeeting(id:name:)` returns the committed record, or the unchanged record for a normalized no-op. A missing ID is an error. Read the affected row and commit before returning success.

Persist `updatedAt` as finite epoch seconds. Within `BEGIN IMMEDIATE`, choose `max(now, greatestStoredUpdatedAt.nextUp)` for actual writes (or now if empty), rejecting non-finite results. This small logical-clock adjustment ensures rapid writes and backward wall-clock changes still make the latest successful change first. Load with `updatedAt DESC, id ASC`; canonical UUID ties are stable. Backfill legacy timestamps from `createdAt`, preserving their existing order. Do not rely on hidden rowid.

Return mutation results directly to ContentView and merge/sort them in the existing loaded list using the same comparator; avoid a second fallible load after commit. Serialize UI mutations and disable overlapping submissions. Loading errors retain the existing startup/retry flow; mutation errors remain separate from load state and preserve the current list and destination.

### Interaction

Replace the fixed Meetings heading with a compact heading row and plus Button. Keep it above the scroll area. Disable it until storage loads and while a mutation is pending. A successful create merges the result, sets the destination by UUID, and scrolls to the new row.

Keep exactly one rename session: Meeting ID, origin (sidebar/header), draft, validation/save error, and pending action if navigation or creation caused focus loss. Double-clicking a row selects it and opens its inline editor. A single click still selects; test gesture precedence in the native app. A context-menu Rename action and Shift-Command-R for the focused Meeting/title offer keyboard access. Use native TextField with distinct FocusState targets and an accessible label.

Enter or loss of focus commits a valid changed name; Escape cancels. Before changing destination, creating a Meeting, or opening another editor, finish the current edit. Invalid drafts or failed saves retain editing and prevent that pending action. Deduplicate Enter/focus-loss commits, disable edits while saving, and execute a pending action once. The other name location displays the saved value until commit. Keep selection anchored to UUID when reorder occurs and reveal the renamed row without moving focus to another Meeting.

Normalize names by trimming surrounding whitespace/newlines; reject empty names and embedded NUL, allow Unicode, punctuation, and duplicates, and perform no arbitrary length truncation in storage. Use a small built-in English adjective/noun name generator, with no naming dependency. Translate strings in touched views and store errors to English; leave unrelated documents alone.

### Meeting workspace

Place the editable title above a macOS-14-compatible TabView with one `.tabItem` containing `Label("Transcription", systemImage: "text.alignleft")`. The selected content shows "No transcription yet." Use the existing system typography/colors. Verify that the native tab style displays both icon and label; if the default style suppresses the icon, use a compact native-styled labeled tab header with selected accessibility state. Do not ship an invisible icon or introduce newer macOS-only APIs. Add no tabs beyond Transcription and no future extensibility framework.

### Validation and sequence

First extend storage and meaningful persistence tests, then wire creation, rename, and detail presentation. Update existing fixtures for the new initializer/schema, particularly positional inserts and tests that currently treat schema v2 as unsupported (use v3). Preserve a dedicated legacy-v1 fixture for migration. Test bind safety with apostrophes/Unicode and validation with blank/NUL input.

Run build and the existing suite; run the native bundle with an isolated data directory. Verify all acceptance scenarios, 100-row creation timing, restart persistence, migration, rename via both surfaces, failure/retry, keyboard/VoiceOver, double-click versus single-click, minimum window, and light/dark appearance. Record actual evidence and limitations in validation.md during implementation. No implementation, build, or UI verification is claimed by this plan.
